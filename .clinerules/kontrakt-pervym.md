# Изменение API начинается с контракта

Источник истины это `contract/main.tsp`. Файл `contract/openapi.yaml` из него собирается
и в репозиторий коммитится. Тест `server/tests/contract.test.ts` читает `openapi.yaml`
и требует, чтобы приложение ему подчинялось.

## Порядок, который нельзя переставлять

1. Правлю `contract/main.tsp`.
2. Пересобираю контракт: `npm run contract:build`.
3. Привожу схемы Zod в `server/src/schemas.ts` в соответствие с контрактом.
4. Правлю обработчики в `server/src/routes/`.
5. Правлю типы в `web/src/api.ts`.
6. Запускаю `npm test`.

## Что делать нельзя

Начинать с обработчика. Если первым правится `server/src/routes/`, падает
`contract.test.ts`, и это не поломка теста, а его работа.

Править `contract/openapi.yaml` руками. Он собирается из `main.tsp`, ручная правка
теряется при следующей сборке, а непрерывная интеграция сравнивает собранный файл
с закоммиченным и валит сборку.

## Как я проверяю себя

Перед тем как сказать «готово», выполняю обе команды и показываю вывод целиком:

```bash
npm run typecheck
npm test
```

Ожидаемые строки: `Test Files 6 passed (6)` и `Tests 65 passed (65)`. Если число тестов
выросло, называю, какие тесты добавил и что именно они проверяют.
