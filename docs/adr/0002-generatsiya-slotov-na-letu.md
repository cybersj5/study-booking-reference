# ADR 0002. Генерация тайм-слотов на лету, а не хранение в базе

- **Статус:** принято
- **Дата:** 29 сентября 2026
- **Авторы:** команда курса «ИИ для разработчиков», СФУ

## Контекст

Расписание задаётся правилом: дни недели, рабочее окно (например, с 10:00
до 13:00) и шаг сетки. Из правила получается набор конкретных тайм-слотов
на конкретные даты.

Нужно решить, где живут слоты: в отдельной таблице базы данных или вычисляются
при каждом запросе.

Особенности задачи:

- Слот полностью определяется расписанием, длительностью активности и датой.
  Своих данных у слота нет, кроме признака «занят или свободен».
- Признак занятости выводится из таблицы броней.
- Расписание бессрочное: слоты можно спрашивать на любую будущую дату.
- Диапазон запроса ограничен 60 днями, смотри `MAX_RANGE_DAYS`
  в `server/src/slotEngine.ts`.

## Рассмотренные варианты

**Таблица `slots` с заранее сгенерированными строками.** Позволила бы ссылаться
на слот по идентификатору и повесить уникальное ограничение прямо на `slot_id`.
Отклонено: появляется задача поддержания таблицы в актуальном состоянии.
При правке расписания нужно решать, что делать с уже созданными слотами,
на которые есть брони. Для учебного проекта это лишняя сложность.

**Генерация слотов на фиксированный период вперёд, например на 90 дней.**
Компромисс между двумя вариантами. Отклонено: требует планировщика задач,
а его появление в проекте пришлось бы объяснять отдельно.

**Вычисление слотов на стороне интерфейса.** Сервер отдавал бы расписания
и брони, браузер считал бы сетку. Отклонено: правило генерации слотов это
бизнес-логика, её нельзя дублировать в двух местах. Кроме того, при проверке
брони серверу всё равно пришлось бы считать сетку самостоятельно.

## Решение

Слоты не хранятся. Они вычисляются при каждом запросе `GET /api/slots`
функцией `buildSlots` в `server/src/slotEngine.ts`.

Функции этого модуля чистые: они принимают активность, список расписаний,
список занятых пар «дата и время» и границы диапазона, а возвращают список
слотов. В базу данных они не ходят. За выборку данных отвечает обработчик
маршрута `server/src/routes/slots.ts`.

Признак `is_free` вычисляется проверкой пары «дата и время начала» по множеству
`Set`, собранному из действующих броней.

## Последствия

**Положительные:**

- Нет задачи синхронизации. При изменении расписания не нужно пересоздавать
  заранее сгенерированные слоты, старые слоты не устаревают.
- Нет фоновых задач и планировщика, который заполнял бы таблицу слотов вперёд.
- Слоты доступны на любую дату в будущем, а не только на заранее
  сгенерированный период.
- Логика собрана в одном файле и покрыта тестами без участия базы данных.
  Тесты в `server/tests/slotEngine.test.ts` работают с обычными объектами
  и выполняются за миллисекунды.
- Студенту видно, что «сущность в предметной области» и «таблица в базе» это
  разные вещи. Это важная мысль курса.

**Отрицательные:**

- Каждый запрос слотов делает вычисление заново. При 60 днях и шаге 15 минут
  это тысячи объектов на запрос. Для учебного сервиса приемлемо, для крупного
  сервиса потребовалось бы кеширование.
- На слот нельзя сослаться по идентификатору. Бронь ссылается на тройку
  «активность, дата, время начала», а не на `slot_id`.
- Нужна отдельная проверка, что запрошенное время действительно есть в сетке.
  Её делает функция `findSlot`, она вызывается перед созданием брони.
  Без неё гость мог бы забронировать произвольное время, например 10:07.
- Диапазон запроса приходится ограничивать, иначе один запрос на десять лет
  создаст десятки тысяч объектов.
