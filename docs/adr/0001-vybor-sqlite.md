# ADR 0001. Хранилище: SQLite через синхронный драйвер better-sqlite3

- **Статус:** принято
- **Дата:** 28 сентября 2026
- **Авторы:** команда курса «ИИ для разработчиков», СФУ

## Контекст

Сервису нужно хранить три сущности: виды активности, расписания и брони.
Объём данных небольшой: десятки активностей, сотни броней.

Проект является эталонным для учебного курса. Его будут запускать 6–14 студентов
на своих ноутбуках, преимущественно под Windows, в аудитории, в пределах одного занятия.
Дополнительные ограничения:

- Занятие ограничено по времени: от 2 до 6 ак. часов. Время на настройку окружения
  нужно свести к минимуму, иначе на саму разработку его не останется.
- Аудитории меняются от занятия к занятию, стабильность сети не гарантирована.
- Docker студенты видят на этом курсе впервые, поэтому сервис должен
  запускаться и без него, одной командой `npm run dev`.
- Модули на C++ под Windows это отдельная боль: если пакет придётся собирать
  из исходников, понадобятся средства сборки Visual Studio, и занятие уйдёт
  на их установку.

## Рассмотренные варианты

**PostgreSQL в Docker.** Ближе к промышленной практике и снимает ограничение
на одновременную запись. Отклонено: студенту пришлось бы поднять контейнер
до первой строки кода, а Docker Desktop под Windows у части группы не заработает
с первого раза. Это съело бы занятие целиком.

**Встроенный модуль `node:sqlite`.** Появился в Node.js 22 и не требует
вообще никаких зависимостей. Отклонено: на момент написания он помечен как
экспериментальный, при запуске печатает предупреждение и меняет API между
версиями Node.js. Для материала, который должен одинаково собираться через
полгода, это неприемлемо.

**ORM (Prisma, Drizzle, TypeORM).** Дала бы типы для запросов и миграции.
Отклонено: любая из них добавляет собственный язык описания схемы и шаг
генерации кода, а курс и так вводит TypeSpec, Docker, тесты и агентов. Кроме
того, частичный уникальный индекс пришлось бы всё равно писать сырым SQL.

**Хранение в JSON-файле.** Не требует ничего. Отклонено: пришлось бы
самостоятельно писать блокировки и проверки целостности, а главное, студенты
не увидели бы ни транзакций, ни уникальных индексов. Защита от двойного
бронирования на уровне базы стала бы невозможной.

**Хранение в памяти процесса.** Самый простой вариант. Отклонено: данные
исчезают при перезапуске, поэтому демонстрация «забронировали, перезапустили,
бронь на месте» не получилась бы.

## Решение

Используем SQLite через `better-sqlite3` версии 13. Файл базы `booking.db`
создаётся автоматически при первом запуске в корне проекта. Путь к файлу
меняется переменной окружения `BOOKING_DB_FILE`, этим пользуются
`docker-compose.yml` и сквозные тесты.

Драйвер выбран синхронный. Запрос возвращает результат сразу, без промисов
и `await`. Асинхронный драйвер `node:sqlite` или `sqlite3` дал бы привычный
для Node.js стиль, но в обработчиках появилось бы по три-четыре `await`
на каждый запрос без всякой пользы: обращения к локальному файлу занимают
десятки микросекунд.

Весь SQL собран в одном файле `server/src/repository.ts`. Обработчики маршрутов
вызывают его функции и не пишут запросы сами.

## Последствия

**Положительные:**

- Установка сводится к `npm install`. Отдельный сервер базы данных ставить
  не нужно, порты настраивать не нужно.
- `better-sqlite3` версии 13 поставляет готовые сборки для Windows, macOS
  и Linux, включая процессоры ARM. Компилятор на машине студента не нужен.
- Тесты работают быстро: каждый тест получает свою базу в оперативной памяти
  (`:memory:`), все 65 тестов проходят примерно за 3 секунды.
- Начать с чистого состояния можно удалением одного файла.
- Синхронный драйвер убирает из кода состояние гонки внутри одного запроса:
  между проверкой и записью не может вклиниться другая задача цикла событий.
- Прямой SQL виден студенту целиком. ORM спрятала бы и запросы, и частичный
  индекс, ради которого затевалась защита от двойного бронирования.

**Отрицательные:**

- SQLite плохо переносит одновременную запись из многих процессов. Для учебного
  сервиса с одним процессом это не проблема, для промышленной нагрузки было бы
  проблемой.
- Синхронный драйвер блокирует цикл событий на время запроса. При запросах
  на десятки миллисекунд это стало бы узким местом, здесь запросы короткие.
- Нет отдельных типов для даты и времени: они хранятся строками
  «ГГГГ-ММ-ДД» и «ЧЧ:ММ:СС». Формат выбран так, что строки сравниваются
  и сортируются как сами моменты времени.
- Частичный уникальный индекс (`WHERE status = 'active'`) есть в SQLite
  и PostgreSQL, но не во всех базах. Смотри ADR 0003.
- Миграций в проекте нет. При изменении структуры таблиц базу нужно удалить
  и наполнить заново. Для учебного проекта это приемлемо.
- Запросы написаны руками, значит опечатка в имени столбца выяснится
  во время выполнения, а не при проверке типов. Это компенсируется тем,
  что все запросы собраны в одном файле и покрыты тестами.
