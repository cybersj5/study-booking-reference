# PDR 0001. Сервис бронирования тайм-слотов

- **Статус:** принято
- **Дата:** 28 сентября 2026
- **Тип документа:** продуктовое решение (Product Decision Record)
- **Авторы:** команда курса «ИИ для разработчиков», СФУ

## Задача

Преподавателю, руководителю проекта или консультанту нужно принимать людей
по записи. Сейчас это делается перепиской: гость пишет «когда вам удобно»,
получает список вариантов, выбирает, хозяин календаря вписывает встречу
в календарь вручную.

Переписка занимает от трёх до восьми сообщений на одну встречу. При десяти
встречах в неделю это заметная нагрузка. Дополнительно возникают ошибки:
на одно время записываются двое, встреча теряется, гость не помнит, когда
записался.

## Кому это нужно

**Организатор.** Заводит виды активности и часы приёма один раз, дальше
не участвует в согласовании. Хочет видеть, что на одно время не записаны двое.

**Гость.** Хочет открыть ссылку, увидеть свободное время и записаться
за одно действие. Регистрироваться и заводить пароль не хочет.

## Что решает сервис

1. Показывает свободное время без переписки. Гость видит сетку слотов
   на неделю и переключает недели вперёд и назад.
2. Не даёт записаться двоим на одно время. Занятый слот показан штриховкой,
   а попытка забронировать его запросом к API получает отказ с кодом 409
   и кодом ошибки `slot_taken`.
3. Разделяет виды встреч. У консультации на 30 минут и защиты проекта на час
   разная длительность и разные часы приёма.
4. Отменяет бронь. После отмены слот снова свободен, а запись
   об отмене сохраняется.
5. Даёт гостю посмотреть свои брони по адресу почты, без регистрации.

## Сценарии использования

**Сценарий 1. Запись на консультацию.**
Гость открывает страницу, выбирает активность «Консультация по проекту»,
видит сетку на неделю. Занятые слоты отмечены штриховкой. Гость нажимает
на свободный слот, вводит имя и почту, нажимает «Забронировать». В правой
колонке появляется подтверждение, слот становится занятым, бронь появляется
в блоке «Мои брони».

**Сценарий 2. Попытка занять уже занятое время.**
Двое гостей открыли страницу одновременно и выбрали один слот. Первый успевает
забронировать. Второй нажимает «Забронировать» и получает сообщение «Этот слот
уже забронирован». Сетка обновляется, слот показан занятым.

**Сценарий 3. Отмена.**
Гость видит блок «Мои брони», подставленный по введённой почте, нажимает
«Отменить». Бронь получает статус «отменена», слот снова доступен другим гостям.

**Сценарий 4. Настройка расписания организатором.**
Организатор двумя запросами к API создаёт активность «Код-ревью»
длительностью 45 минут и расписание: вторник и четверг, с 14:00 до 18:00,
шаг 60 минут. Сервис сам строит сетку слотов на все будущие даты.

## Что осознанно не делается в этой версии

| Не делаем | Почему |
|---|---|
| Учётные записи и пароли | Гость опознаётся адресом почты. Регистрация отпугивает и не нужна для записи на встречу |
| Письма с подтверждением | Требует почтового сервиса и настройки. Для учебного проекта это отдельная тема |
| Часовые пояса | Все участники курса в одном городе. Поддержка поясов удвоила бы сложность работы со временем |
| Запрет на бронирование прошедшего времени | Требует понятия «сейчас» в бизнес-правилах и делает тесты зависящими от даты запуска. Прошедшие дни в интерфейсе показаны приглушённо |
| Перенос брони | Заменяется двумя действиями: отменить и забронировать заново |
| Исключения в расписании: праздники, отпуск | Усложняет модель расписания. Обходится созданием отдельной активности |
| Оплата | Вне задачи |
| Уведомления в мессенджеры | Требует внешних сервисов и ключей доступа |
| Раздел организатора в интерфейсе | Организатор работает через API. Интерфейс сделан для гостя, и это единственный сценарий, который нужно довести до качества |

## Как поймём, что решение работает

- Гость записывается на встречу не более чем за четыре действия: выбрать
  активность, выбрать слот, ввести имя и почту, нажать кнопку.
- Ни при каких условиях в базе не появляется двух действующих броней на один
  слот. Проверяется тестами.
- Организатор настраивает новый вид встреч без изменения кода, двумя запросами
  к API.
