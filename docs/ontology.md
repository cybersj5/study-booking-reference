# Доменная модель сервиса бронирования

Документ описывает предметную область словами и таблицами: какие сущности есть,
из чего они состоят, как связаны и какие правила обязаны выполняться всегда.

Это не описание кода. Код обязан соответствовать этому документу, а не наоборот.
Формальная запись тех же сущностей лежит в `contract/main.tsp`.

## 1. Область одним абзацем

Организатор описывает, на что можно записаться (**вид активности**) и когда он
принимает (**расписание**). Из вида активности и расписания получается сетка
**тайм-слотов** на конкретные даты. Гость выбирает свободный слот и создаёт
**бронь**. Бронь занимает слот. Отменённая бронь слот освобождает.

## 2. Сущности

### Activity, вид активности

То, на что записывается гость. Отвечает на вопрос «что за встреча и сколько
она длится».

| Атрибут | Тип | Обязателен | Смысл |
|---|---|---|---|
| `id` | целое | да | Идентификатор, присваивает база |
| `name` | строка до 100 символов | да | Название, например «Консультация по проекту» |
| `duration_minutes` | целое от 5 до 480 | да | Длительность одной встречи в минутах |
| `description` | строка до 500 символов | нет | Пояснение для гостя, по умолчанию пустое |
| `color` | код цвета вида `#3b5bdb` | нет | Цвет карточки в интерфейсе |

Хранится в таблице `activities`.

Поле `color` относится к представлению, а не к предметной области. Оно вынесено
в модель осознанно: без него интерфейс не смог бы отличать активности цветом.
Держать соответствие «идентификатор и цвет» на стороне клиента означало бы,
что новая активность появляется в интерфейсе бесцветной.

### Schedule, расписание

Правило, по которому строится сетка слотов. Отвечает на вопрос «в какие дни
и часы принимает организатор».

| Атрибут | Тип | Обязателен | Смысл |
|---|---|---|---|
| `id` | целое | да | Идентификатор |
| `activity_id` | целое | да | К какой активности относится расписание |
| `weekdays` | список чисел от 1 до 7 | да | Дни недели. 1 это понедельник, 7 это воскресенье |
| `start_time` | время | да | Начало рабочего окна, например 10:00 |
| `end_time` | время | да | Конец рабочего окна, например 13:00 |
| `step_minutes` | целое от 5 до 480 | да | Шаг сетки в минутах |

Хранится в таблице `schedules`. В базе список дней недели лежит строкой вида
`"1,2,3,4,5"`, наружу отдаётся списком чисел. Преобразование делают функции
`weekdaysToText` и `weekdaysFromText` в `server/src/repository.ts`.

### Slot, тайм-слот

Конкретный промежуток времени на конкретную дату, на который можно записаться.
**В базе данных не хранится**, вычисляется при каждом запросе. Обоснование
в `docs/adr/0002-generatsiya-slotov-na-letu.md`.

| Атрибут | Тип | Смысл |
|---|---|---|
| `activity_id` | целое | Активность, к которой относится слот |
| `schedule_id` | целое | Расписание, из которого получен слот |
| `date` | дата | День слота |
| `start_time` | время | Начало слота |
| `end_time` | время | Конец слота, равен началу плюс длительность активности |
| `is_free` | да или нет | Свободен ли слот на момент запроса |

### Booking, бронь

Запись гостя на конкретный слот.

| Атрибут | Тип | Обязателен | Смысл |
|---|---|---|---|
| `id` | целое | да | Идентификатор |
| `activity_id` | целое | да | Активность |
| `activity_name` | строка | да | Название активности на момент запроса |
| `date` | дата | да | День слота |
| `start_time` | время | да | Начало слота |
| `end_time` | время | да | Конец слота |
| `guest_name` | строка до 100 символов | да | Имя гостя |
| `guest_email` | адрес почты | да | Почта гостя, по ней гость находит свои брони |
| `status` | `active` или `cancelled` | да | Действует бронь или отменена |
| `created_at` | дата и время | да | Момент создания, в UTC |

Хранится в таблице `bookings`. Поля `activity_name` в таблице нет: оно
добавляется запросом при чтении, чтобы клиенту хватило одного обращения
для показа списка броней.

## 3. Связи

| Связь | Кратность | Пояснение |
|---|---|---|
| Activity и Schedule | один ко многим | У одной активности может быть несколько расписаний, например будни утром и суббота днём |
| Activity и Slot | один ко многим | Слоты вычисляются для конкретной активности |
| Schedule и Slot | один ко многим | Каждый слот произошёл ровно из одного расписания |
| Activity и Booking | один ко многим | Все брони активности |
| Slot и Booking | один к одному или ноль | На слоте либо нет действующей брони, либо ровно одна |

Схема связей словами:

```
Activity  1 ------ * Schedule
   |                    |
   |                    | правило генерации
   |                    v
   * ---------------> Slot (не хранится, вычисляется)
   |                    ^
   |                    | занимает
   * ------------- * Booking
```

Удаление активности удаляет её расписания и брони (`ON DELETE CASCADE`).

## 4. Инварианты

Правила, которые обязаны выполняться всегда. Каждое проверено тестами.

| № | Инвариант | Где проверяется |
|---|---|---|
| И1 | На один слот не более одной брони со статусом `active` | Проверка в `server/src/routes/bookings.ts` и уникальный индекс `uq_active_booking` в `server/src/db.ts` |
| И2 | `start_time` расписания строго раньше `end_time` | Проверка при создании расписания в `server/src/routes/schedules.ts` |
| И3 | Слот целиком помещается в рабочее окно расписания | Условие цикла в `timesForSchedule`, `server/src/slotEngine.ts` |
| И4 | `end_time` слота равен `start_time` плюс `duration_minutes` активности | Функция `timesForSchedule`, `server/src/slotEngine.ts` |
| И5 | Бронь возможна только на время, которое есть в сетке слотов | Функция `findSlot`, вызывается перед созданием брони |
| И6 | Дни недели расписания это числа от 1 до 7, список не пуст | Схема `scheduleCreateSchema` в `server/src/schemas.ts` |
| И7 | Длительность активности от 5 до 480 минут | Схема `activityCreateSchema` в `server/src/schemas.ts` |
| И8 | Отменённая бронь освобождает слот и не мешает новой брони | Условие `status = 'active'` в индексе и в запросах |
| И9 | Отменить можно только действующую бронь | Проверка в обработчике отмены, `server/src/routes/bookings.ts` |
| И10 | Запрашиваемый диапазон дат не длиннее 60 дней и начало не позже конца | Проверки в `server/src/routes/slots.ts` |

## 5. Жизненный цикл брони

```
      создание           отмена
  ---------------> active ---------> cancelled
                     |                   |
                     | слот занят        | слот снова свободен
```

Состояния всего два. Возврата из `cancelled` в `active` нет: чтобы вернуть
время, нужно создать новую бронь.

## 6. Словарь терминов

| Термин | Значение в этом проекте |
|---|---|
| Вид активности | То, на что записываются: консультация, код-ревью, защита проекта |
| Расписание | Правило «дни недели плюс рабочее окно плюс шаг», из которого строится сетка |
| Рабочее окно | Промежуток от `start_time` до `end_time` внутри одного дня |
| Шаг сетки | Через сколько минут начинается следующий слот. Может отличаться от длительности |
| Тайм-слот | Конкретный промежуток на конкретную дату, на который можно записаться |
| Бронь | Запись конкретного гостя на конкретный слот |
| Гость | Тот, кто записывается. Учётной записи у него нет, он опознаётся по почте |
| Организатор | Тот, кто заводит активности и расписания |

## 7. Пример

Активность: «Консультация по проекту», длительность 30 минут.
Расписание: дни недели 1–5, окно с 10:00 до 12:00, шаг 30 минут.

Сетка на понедельник:

| Слот | Начало | Конец |
|---|---|---|
| 1 | 10:00 | 10:30 |
| 2 | 10:30 | 11:00 |
| 3 | 11:00 | 11:30 |
| 4 | 11:30 | 12:00 |

Если поменять длительность активности на 45 минут, сетка станет другой:

| Слот | Начало | Конец |
|---|---|---|
| 1 | 10:00 | 10:45 |
| 2 | 10:30 | 11:15 |
| 3 | 11:00 | 11:45 |

Слот с началом в 11:30 закончился бы в 12:15 и вышел бы за рабочее окно,
поэтому в сетку он не попадает (инвариант И3). Слоты при этом накладываются
друг на друга, потому что шаг сетки меньше длительности. Это допустимо:
как только один слот забронирован, остальные остаются свободными, и организатор
сам решает, задавать ли такой шаг.
